# Layout reproducibility: `flow/layout.sh` today vs the committed klt-0.5.0 layout (issue #245)

**Verdict: `physical`.** The current toolchain does not reproduce the committed
`layout/logic_tile.{gds,def,par.json}`, and the difference is in placement and
routing, not in formatting, ordering or provenance. 45 of the 47 logic cells sit
at different coordinates and all 137 nets are routed differently. Cell masters,
netlist connectivity, die area, pins, tap cells, `SPECIALNETS` and `VIAS` are
unchanged. Every timing and DRC verdict still passes and the numbers moved only
slightly (below).

## Method

One `./flow/layout.sh` in default check mode (no `--update`), run on the
dispatch host, about 44 s. It was run twice, once per PDK install present on the
host, to separate PDK drift from toolchain drift:

| run | PDK | command |
|---|---|---|
| A | `open_pdks f6eeac7d…` (`~/.ciel`, the default resolution) | `./flow/layout.sh` |
| B | `open_pdks c6d73a35…` (`RECORDED_PDK_VERSION`, `~/.volare`) | `PDK_ROOT=~/.volare PDK=sky130A ./flow/layout.sh` |

Run A's DEF is byte-identical to run B's, and `klt diff` calls their GDS
byte-identical. The PDK revision does not matter for this flow, so the drift is
the klt/OpenROAD change. All tables below are run B, the recorded PDK. Both runs
exit 1 with the GDS, DEF and report all reported as differing.

| tool | recorded (committed lineage) | installed here |
|---|---|---|
| klt | `0.5.0+g2b7caa9939af` | `0.9.2.dev246+g2faba5dec206` |
| OpenROAD | `26Q3-1278-g4421880472` | `26Q3-1510-g6cb3f2b704` |
| yosys | native (version not pinned for the layout lineage) | native, `~/.local/bin/yosys` |
| sky130A PDK | `open_pdks c6d73a35…` | run B: same; run A: `f6eeac7d…` |

The installed klt is a development build (`0.9.2.dev246`), not the `0.8.0` PyPI
release `flow/README.md` §0.8.0 refers to. So this record measures the klt on
this host, not the release. It was not re-run under `uvx --from
"klayout-tools==0.8.0"`. Comparisons were made with a throwaway parser over the
two DEF files (kept out of the tree) and with `klt diff` / `klt stats` on the
GDS.

## GDS (`layout/logic_tile.gds`, 174606 B vs 177848 B regenerated)

`klt diff` (geometry-only; ignores timestamps, order, library name): **different**.
The regenerated stream has one extra cell, `VIA_M3M4_PR`; within `logic_tile` layer
68/20 has 265 shapes only in the committed GDS and 285 only in the regenerated one,
69/20 248 vs 270, 70/20 69 vs 68, 71/20 0 vs 2; instances 665 only in the
committed vs 649 only in the regenerated. `klt stats` polygons 1594 -> 1640,
vertices 7304 -> 7488, area 10749.07 -> 10769.51 µm², bbox unchanged
(44.33 × 44.33 µm). An XOR of the layers was not run (no XOR verb was used
beyond `klt diff`).

## What this record does NOT claim

- It does not say the regenerated layout is DRC/LVS/ERC clean. Only the
  place-and-route report's own counts (route DRC 0, antenna 0) are compared.
  `flow/drc.sh`, `flow/lvs.sh` and `flow/erc.sh` were not run on it.
- It does not attribute the change to a single klt or OpenROAD commit: two
  versions moved at once (see the table at the top), and the klt is a
  development build.
- It does not re-characterize timing. SPEF/SDF evidence under
  `measurements/timing-characterization/` is untouched.
- Nothing under `layout/` was regenerated or committed.

## Follow-up

Physical drift, so a successor timing record cannot assume the committed geometry
is what the current flow produces. Needed: a re-layout + re-stamp issue (run
`./flow/layout.sh --update` deliberately, then re-run DRC/LVS/ERC and the STA
sweep and re-stamp the dependents), or an explicit decision to keep the
klt-0.5.0 geometry as frozen evidence and pin the toolchain that made it. Either
choice gates #162 and #213. That issue is not filed by this record.
